# Sous — Vision

## In one sentence

A personal recipe management and meal planning app for iOS/macOS in the spirit of Mela — but with local AI integration for recipe generation, leftover cooking, web research, and automated, nutrient-optimized weekly meal planning.

## Starting point

Mela is currently in use and is broadly satisfactory, but appears to no longer be actively developed. Rather than a 1:1 rebuild, this is a distinct app — not a feature clone (RSS feeds, for example, are deliberately left out) — with meaningful AI value on top, which Mela lacks.

## Guiding principle for the AI architecture

**The right tool for the right job.** AI handles language, structuring, extraction from unstructured sources (web, video), and creative generation. Conventional code and external databases handle arithmetic, nutritional facts, and optimization.

Rationale: language models are unreliable with numbers and facts (plausible-sounding but wrong nutrition values), yet very strong at narrowly scoped structuring tasks — especially with Apple's `@Generable` mechanism, which yields guaranteed-valid, parsed output instead of free-form text. This separation runs through the entire architecture.

## Core features

1. **Recipe management** — list, categories, favorites, "want to cook", a long-press that previews the recipe itself with its actions underneath rather than a bare menu, cook mode, serving scaling, recipes linked from one another (a curry references the naan, which is an ordinary recipe in its own right), and a plan that is either dated or loose — meals sit on a day or in an undated pool, and move between the two — which the optimizer later builds on
2. **AI recipe generation from the personal collection** — new recipes in the user's own style, via retrieval (tool calling against the local database) plus structured generation
3. **Ad-hoc leftover cooking** — free-text input ("zucchini and feta need to go"), no persistent pantry record, reusing the same generation mechanism as feature 2
4. **Recipe variation** — modifying an existing recipe on request ("make this vegetarian", "double the spice"), reusing the same generation mechanism as features 2–3 but scoped to a single source recipe rather than retrieval across the collection, which makes it the cheapest of the three generation-based features. Where the result goes is a data-model question rather than a generation one — it is saved as a sibling variant beside the original rather than over it (see "Recipe variants" below)
5. **Web research for new recipe ideas** — scraping of comparable existing recipes as a tool, using the same structured extraction path as the conventional URL import
6. **Video import (Instagram/TikTok/YouTube)** — implemented as a **share extension**: the user shares a post into the app, and the app processes what it is handed rather than fetching from the platform itself (see Distribution below). Where a video file is available, actual video analysis applies: keyframes through Vision framework OCR (on-screen text), audio track transcribed through the Speech framework, fed into the same extractor together with the caption. Not "video understanding" by a single model — this is decomposition into text, not true video comprehension, but it covers the cases where the caption does not carry everything.
7. **Per-recipe nutrition** — ingredients extracted and normalized structurally (AI), matched against an external nutrition database (conventional code)
8. **Shopping list** — assembled from a stretch of planned days or from the undated pool, with amounts of the same ingredient added together
9. **Automatic, nutrient-optimized weekly plan** — deterministic algorithm against a nutrient/calorie target vector, drawing first on what is already in the undated pool and then on the recipes the user has marked "want to cook"; AI is used only to generate new recipes when the existing recipe pool cannot close a gap
10. **Household sharing** — a household is the unit of sharing: one owner invites members, and the household's recipes and meal plans are shared with all of them. Individual profiles (diet, exercise load, etc.) stay personal and feed into personal nutrition targets.

## Technical architecture pillars

* **Foundation Models framework** (on-device, `@Generable`, tool calling) as the baseline on both iPhone and Mac — free, offline, private
* **MLX as a swappable, stronger backend on the Mac** for tasks where the 3B system model is too bland (primarily creative recipe generation). Since WWDC 2026 the framework sits behind a `LanguageModel` protocol with interchangeable backends — the on-device system model, Private Cloud Compute, Core AI for custom weights, and `MLXLanguageModel` for Hugging Face MLX models — so the backend can be swapped per feature without touching the feature code.
  * **To verify before relying on this (one-day spike, not yet run):** whether guided generation (`@Generable`) and tool calling behave with the same guarantees on arbitrary MLX models as they do on the system model — constrained decoding is model-dependent; whether a small on-device-tier model reliably picks the right tool among several registered ones; and how much context headroom actually remains after a tool call when a generation follows in the same session.
  * **Candidates**: Mistral Small 4 (shipped March 2026), Soofi S (German/European consortium — Fraunhofer IAIS/IIS, DFKI, TU Darmstadt, Uni Würzburg — 30B total/3.2B active MoE, strong German-language benchmarks; license and MLX-format availability unconfirmed as of writing), optionally a Gemma or Qwen model as a reference point. Chosen for European provenance where practical — the final pick depends on spike results, not on name recognition. License terms for whichever model is actually offered are checked at the point of integrating it, not speculatively in advance.
* **Private Cloud Compute (PCC) as a third backend, for on-device-grade privacy with more headroom.** Same unified API as the system model — `@Generable` and tool calling work identically — with a documented ~32,000-token context window against the system model's 4096. Free for developers in the App Store Small Business Program under 2 million first-time downloads; past that threshold there is currently no paid tier at all — access simply ends, and a user's iCloud+ subscription grants no extra quota for third-party apps. This makes PCC suitable as a visible, user-facing escalation within a session (see the chat section below), never as the foundation a core feature is built to depend on, since it can be withdrawn without recourse.
* **MLX model delivery is on-demand, never bundled.** No model weights ship inside the app binary — bundling would bloat the App Store download for a capability most iPhone users will never touch. Instead, the Mac-only generation feature surfaces a visible, explicit invitation ("download a stronger model for better results") when it becomes relevant; nothing downloads automatically on first launch or on first opening the feature. Once accepted, the model is fetched (MLX-converted, from Hugging Face) and cached locally.
* **Context budget is a hard design constraint.** The on-device system model has a fixed 4096-token context window per session, and instructions, tool definitions, the `@Generable` schema, and the running transcript all count against it. A full recipe costs roughly 500–1000 tokens, so only two or three retrieval hits fit. Retrieval must therefore return condensed recipe profiles (style markers, ingredient signature) rather than full text, with pre-selection done in conventional code. `contextSize` and `tokenCount(for:)` (iOS 26.4+) are used to budget this explicitly rather than guessing.
* **Mac and iPhone run independently.** Where the iPhone is too weak for a task, that is accepted, or offloaded to a self-hosted Ollama server or a paid cloud API (Claude/ChatGPT — billed separately from the chat subscription, pay-per-token). Recipe generation grounded in the personal collection is expected to be one of those Mac-first features.
* **Local-first persistence with SwiftData.** The device holds the authoritative working copy. Search, filtering, serving scaling, nutrition calculation against the locally cached BLS data, and retrieval for the AI features all run against the local store — they have to, both for offline use and because the AI features need local data anyway.
* **Supabase as an encrypted sync layer, not as a query backend.** Android is a plausible future target, which rules out CloudKit; and the operator (i.e. the developer) must not be able to read user data, which rules out any backend that queries the data server-side. These two together mean the server is a transport and access-control layer only:
  * **Plaintext in Postgres:** household membership, blob IDs and their household, timestamps, tombstones, and per-member wrapped keys. Row Level Security governs which rows a client may fetch at all.
  * **Ciphertext:** recipes, meal plans, and profiles, encrypted client-side.
  * **Images are their own blobs**, referenced by the recipe rather than embedded in it (where Mela's format puts them as base64). They are large and rarely change, so inlining them would mean re-encrypting and re-uploading every photo whenever a word of the text changes. They are downsized on import — a stored image is at most 2048px on its long edge, with a 400px thumbnail beside it for lists.
  * **Key model:** one symmetric AES-256-GCM key per household, wrapped for each member with their X25519 public key; private keys live in the Keychain / Android Keystore, backed by a recovery passphrase. No forward secrecy and no asynchronous delivery to strangers are needed, which keeps the scheme small.
  * **The crypto is implemented in-house**, behind a narrow protocol (`encrypt`, `decrypt`, `wrapKeyFor`, `rotate`) so a managed SDK could still replace it later. This is the well-trodden path, not the exotic one: Bitwarden, 1Password, Ente, Proton, Standard Notes, and Anytype all implement this same pattern and none of them uses an E2EE SDK. Bitwarden calls it the Organization Symmetric Key, Ente calls it the Collection Key; here it is the household key. The Bitwarden security whitepaper serves as the specification and Ente's open-source code as the reference implementation. The managed alternatives (Seald, Tanker, Virgil E3Kit, IronCore) were evaluated and rejected: pricing is not public, the market has consolidated into acquisitions by companies serving their own needs (Seald → OVHcloud, Tanker → Doctolib), and switching provider later means re-keying every user at once.
  * **Note on what this rules out:** no server-side filtering, sorting, joins, or full-text search over recipe content, and metadata (who is in which household, how many recipes, when they changed) remains visible to the operator. Encrypting metadata as well is a different order of magnitude and out of scope.
* **User management: authentication and decryption are deliberately separate.** Supabase Auth answers who may log in; it cannot answer who may read, because any secret it verifies is a secret the server has seen.
  * **Login** through Supabase Auth (Sign in with Apple on iOS, Google on Android).
  * **Decryption** through a separate passphrase the server never receives. Argon2id derives a key from it, which encrypts the user's X25519 private key; the wrapped private key may then be stored server-side, since it is worthless without the passphrase. A new device logs in, fetches the wrapped key, and unwraps it locally — no device-to-device pairing needed, which removes most of the multi-device complexity.
  * Two secrets instead of one is the honest cost, and the passphrase is unrecoverable: issuing a recovery code at signup is mandatory, not optional.
  * **Inviting a member requires an existing member to come online**, because the household key can only be wrapped once the invitee's public key exists — the server cannot do it. An invitation therefore has a pending state. Putting the secret in the invitation link instead avoids this but exposes it to whichever messenger carries the link.
  * **The planning-relevant part of a profile must live under the household key**, not privately: the weekly plan optimizer computes shared meals across all participating profiles, so the device doing the computation must be able to read the others' diets, allergies, and target vectors. Private profiles and shared planning are mutually exclusive. Profiles therefore split into a household-visible part (diet, allergies, nutrient targets) and a private remainder.
* **Requirements this places on the phase-1 data model** — cheap now, a migration later:
  * A recipe is a self-contained aggregate (recipe + ingredients + steps) that serializes as one unit
  * Stable UUIDs rather than autoincrement IDs, so records created offline sync without collisions
  * `updatedAt` and a tombstone flag from the start, because deletions cannot be retrofitted into a sync protocol
  * `createdBy`, and later a household reference, on every recipe
* **Distribution: App Store.** This rules out fetching media from Instagram/TikTok directly — under App Store Review Guideline 5.2.3, apps that download third-party media without platform authorization are rejected, including when official APIs are used. Hence the share-extension design for video import. Importing a recipe from a URL the user supplies is unaffected and remains standard practice.
* **Nutrition data:** Bundeslebensmittelschlüssel (BLS) 4.0 as the primary source — license-free since 2025-12-16 under CC BY 4.0 (attribution to Max Rubner-Institut required in-app), ~7,140 foods, 138 nutrients, German-language. It is a curated staple-ingredient catalog rather than a barcode catalog, which is exactly what recipes need, and it largely removes the German→English ingredient normalization problem. USDA FoodData Central (CC0) and Open Food Facts serve as supplements for branded and packaged products.
* **Weekly plan optimizer:** greedy construction followed by local swap improvement, scored by a cost function with asymmetric penalties (see below), plus variety and cooking-effort constraints.

## Recipe variants — siblings in a group

**A recipe variant is a sibling, not a derivation — variants sit side by side in a group that is not itself a recipe.** Feature 4 modifies a recipe on request, and where the result goes is a data-model question rather than a generation one. Both obvious answers lose something: overwriting the original destroys it, and saving an unrelated new recipe leaves the collection holding two "Chili con Carne" that know nothing about each other. Neither survives the point where there are five of them. The place is built; the generation that fills it waits on the MLX spike, and "add a variant" meanwhile makes the copy a person then edits.

* **Every variant is a full, ordinary recipe, never a stored delta on a base.** A delta means the variant has no text of its own, which contradicts the rule above — text is the truth — and turns an edit to the base into a merge against free-form prose, inside an end-to-end encrypted store where the conflict may surface days later on another device. A copy costs almost nothing here, because the text is very nearly the whole aggregate. Pictures are the exception and do not come along: `StoredRecipeImage` owns a `recipeID`, so copied `imageIDs` would point at rows belonging to the original, and `RecipeLibrary.save` prunes by that ownership — the variant would carry ids that render nothing. A variant therefore starts without pictures and gets its own. Sharing them becomes free only once images are household blobs a recipe merely references, which the sync section already envisages and the current store does not do. The favourite star and the "will ich kochen" mark stay behind for a different reason: both are judgments about a recipe someone has cooked, and nobody has cooked this one yet — a copied wish would also say the same thing twice to a week that can act on only one of them.
* **What a delta would save is largest exactly where the feature is least justified.** The case for inheritance is "add lentils once, have them in all five". It only holds while the five places are the same place, and the more the variants actually diverge — the vegetarian one already counts lentils as its protein, the quick one has no 25 minutes to give them — the less often that is true. Where variants stay near-identical enough for a delta to apply cleanly, a note on a single recipe would have done the job.
* **Ingredients would merge and steps would not**, which is worth naming because a partial delta is the tempting middle. The ingredient list is a set, so "+ 400 g Linsen" merges without needing context; the instructions are a sequence, and where "Linsen mitanschwitzen" belongs differs per variant by construction. That is not a merge problem but a question of meaning, and it has no computable answer. Half-inherited recipes are worse than uninherited ones, because the user has to learn which half.
* **What the delta promised is delivered as propagation instead** — designed, not yet built. Editing one variant may offer to carry the change into its siblings: previewed, per sibling, deselectable. The difference from inheritance is when the merge happens and what a failure costs: a derivation merges on every render, indefinitely, and fails as a recipe silently showing something nobody wrote; a propagation merges once, with the cook present, and fails as a checkbox left unticked. Since the group is symmetric, so is the offer — there is no base to push from. For genuinely shared components (a dough, a sauce) neither is needed: they are their own recipe, referenced through `RecipeLink` the way a curry references its naan.
* **The group is symmetric and has no head.** No variant is the canonical one. A parent recipe with children hanging off it needs promotion and demotion the first time the version with meat is retired for good — and retiring it is the ordinary case, not an edge one.
* **The group stores a title and essentially nothing else.** The order of its members is their creation order, and dissolving a group is clearing the field on them. Only the title resists derivation: the longest common prefix of "Chili con Carne" and "Linseneintopf mit Chili" is not a name. It is stored once, on the group, rather than repeated on every member — members that disagreed about the dish's name after two devices renamed it would leave nothing able to decide between them.
* **The group is not a recipe, and the test for that is not whether a field exists but whether anything else branches on it.** Showing the union of its members' categories is free — it is computed and can contradict nothing. Storing categories on the group means `RecipeFilter` has to search two kinds of thing and a recipe can reach one category by two routes. The same line separates a displayed nutrition summary from a stored one, or showing which members carry a "want to cook" mark from storing that mark on the group. Inert text — the title, a description — is harmless; anything another feature reads is not.
* **Plan entries and shopping lists always reference a variant, never the group.** A group has no nutrient vector and no serving count, so there is nothing to seat in a week, and a "want to cook" mark on it would state a wish the optimizer cannot act on ("some kind of chili" is a different feature, and not this one). This is the invariant everything else rests on.
* **A group is born as the side effect of an action, not as an administrative one.** There is no "create group" command. "Add a variant" on an existing recipe creates the group, puts the original and the copy in it, and asks once for its title, prefilled with the original's.
* **What looks like a group dissolving itself is a drawing rule, not a write.** A group is drawn as a group while at least two of its members are out of the trash; below that the survivor is an ordinary row and the indentation is gone, which is what keeps the list from filling with pointless nesting. Deleting a member therefore changes nothing about the group, and restoring it from the trash puts the pair back together — clearing the survivor's field eagerly would have made that impossible, and a deletion that can still be undone is still a membership. Only erasing a member for good collects the group behind it. Dissolving on purpose stays what it was: clear the field on every member and drop the row.
* **Groups are shown expanded, and a filtered list shows a group with only its matching members.** Searching for "Linsen" may hit one variant in five; the group's row is context around that hit rather than a reason to draw the other four, and it says so — "1 von 5 Varianten" rather than a count that pretends the dish shrank. The group's title needs no search path of its own: search already runs against `StoredRecipe.searchText`, a denormalized column, so folding the group's title into each member's `searchText` makes "Chili" hit the members and the group's row appear because they did. That copy is an index, rebuilt from the group the way `ingredientKeys` is rebuilt from the ingredient text, and renaming a group rewrites it. Always-expanded rows make the list long once there are thirty groups — a per-group collapsed state fixes that later without touching the model.
* **The group's detail view is a comparison, which is the one thing no single recipe can show.** The variants side by side with what distinguishes them — calories, times, and every ingredient line the versions do not write identically, whether that is one of them missing it or all of them calling for a different amount — because the question that screen answers is which of the five to cook tonight. Amounts are compared as they stand and never scaled onto a common serving count: the members may be written for different yields, and normalizing would turn a display into a calculation that can be wrong, or impossible where the units do not convert. Every figure on it is derived from the members, which is what lets the screen be rich while the stored group stays a title. The diff returns here as presentation: computed when drawn, never persisted, and a bad one is an ugly screen rather than a corrupted recipe. A variant links back to its group, or the comparison is reachable only from the list and never from inside a recipe.
* **The group travels with its members through an export.** An archive is a bag of recipe files, so each member's file names the group it belongs to and an import puts the group back together from them. Without it, exporting and re-importing a library would silently turn five variants into five strangers — which is the one place the whole arrangement could be lost without anyone noticing.
* **The cost is a second synced entity.** A small blob — id, title, `updatedAt` — with its own household row. No tombstone: a group is not something the trash holds, and a member left pointing at a row that is gone reads as ungrouped rather than as damage, so the failure heals itself instead of having to be replicated. What does have to merge rather than duplicate is two offline devices each creating a group for the same recipe.

## AI interaction surface — the chat

Search, generation, variation, and the weekly-plan gap-filler (feature 9) share one entry point: a button that opens a sheet as an ephemeral chat.

* **Unambiguous UI actions never touch the model.** Typing in the search field, tapping "generate weekly plan" — these stay on the existing deterministic paths (`RecipeFilter`/`RecipeLibrary`, the optimizer). The chat is reserved for requests that arrive as open natural language and genuinely need language understanding; routing a plain filter query through an LLM would cost tokens and an inference round trip for something `RecipeFilter.suggestions` already does for free.
* **One domain function, two thin surfaces.** Each capability (search, generate, modify, plan-gap-fill) is written once as a plain function, then wrapped separately as a Foundation Models `Tool` (for the in-app chat) and an `AppIntent` (for Siri/Shortcuts/Spotlight) — not shared protocol conformance, but the same underlying logic behind both. Worth doing regardless of chat timing, since App Intents is now the sole framework Siri uses to call into third-party apps (SiriKit deprecated at WWDC 2026).
* **Tool availability is scoped to where the chat was opened, by default.** Opened from a recipe's detail view → only the variation tool is registered; opened from the search field or globally → search and generation; opened from the meal plan → the planning gap-filler. This keeps tool-definition tokens down (a registered-but-unused tool still costs budget) and keeps routing predictable. A request that falls outside the current scope (e.g. "ich suche Nachtisch mit Seidentofu" typed inside a recipe-detail chat) is handled by an explicit UI toggle ("in ganzer Sammlung suchen") that opens a new, broader-scoped session — not by the model silently reaching for tools outside its registered set. To be validated once a prototype exists.
* **Category matching leans on the model; ingredient matching does not.** `Recipe.categories` is free text with only exact case-insensitive matching in the store, so the chat's search tool is handed the live category list (`store.categories()`, small enough to fit the budget) and the model normalizes synonyms itself ("Nachtisch" → whatever the collection actually uses) before calling the tool. Ingredients can't take the same approach — the catalog is far too large (~7,140 BLS entries) to hand to the model — so ingredient resolution stays code-side: catalog exact/alias/plural-strip match, falling back to the existing free-text substring search on a miss, so a structured filter can never return fewer results than a plain search would have.
* **Chat sessions are ephemeral, one per opening of the sheet.** No persistent history across app launches — reloading old transcripts into context on every reopen would only worsen the budget problem for no real benefit, given these are short, targeted requests rather than long-running conversations.
* **Session/budget discipline is backend-dependent.** The on-device system model's fixed 4096-token window (input + output combined) is tight enough that a generation or variation call always gets a fresh, minimal session — sized to just the current request plus its retrieval hits — rather than a compacted version of a longer chat history; compacting risks silently dropping the retrieved recipe profiles the generation is supposed to be grounded in. On PCC (~32k tokens) or a sufficiently large MLX model this is far less pressing, and a simple `tokenCount(for:)` check before generating is enough. Search/conversational turns, as opposed to generation, can be compacted more freely on any backend — losing early context there costs at most a less-targeted answer, not a corrupted result.
* **Escalation past the on-device budget is visible, never silent.** Foundation Models does not auto-fallback to PCC on `exceededContextWindowSize` — that has to be built. When it is, the user sees it happening ("continuing this over a secure Apple cloud connection for a longer answer?") rather than the app quietly switching backends and network dependency behind their back.
* **Closing the sheet discards the conversation by default.** A warning appears only when there is an unsaved generated or modified recipe — an explicit "save/apply" action inside the chat is what actually persists a result, and the surrounding conversation that led to it was never the valuable part.

## Weekly plan optimizer — scoring

The nutrient target vector has mixed constraint directions and must not be treated as a pure deficit-coverage problem:

* **Lower bounds** (protein, fiber, micronutrients) — under-delivery is penalized
* **Upper bounds** (calories, saturated fat, sugar, sodium) — over-delivery is penalized
* **The undated pool is what the optimizer plans with.** Meals in the pool are already decided on — chosen, with a serving count, just not scheduled — which makes them a stronger signal than a "want to cook" mark and the natural material for filling a week. The optimizer therefore seats the pool first, falls back to marked recipes, and only then reaches into the wider collection. **Dated entries are not its to move**: a meal on a Thursday is there because somebody put it there, and rearranging it would make the plan something the cook has to check rather than trust. The optimizer fills what is empty.
* **"Want to cook" is a wish the plan honours** — a recipe the user has marked is one they already decided they feel like eating, which is the one thing a nutrient target vector cannot know. It enters the cost function as a bonus on top of the nutrient score, not as a constraint: the optimizer reaches for marked recipes ahead of the rest of the collection and passes one over only when it cannot be fitted without breaking the bounds. A bonus rather than a hard requirement, because a plan that seats every marked recipe at the cost of the nutrient targets has stopped being an optimizer and become a queue. **Cooking consumes the mark**: it clears itself once the recipe has actually been cooked, not when it is planned — a plan can be rearranged, and a wish the cook never got round to should stay on the list. Otherwise every mark would have to be cleared by hand, and a list nobody prunes stops meaning anything.

* **Variants of the same dish are alternatives, not variety.** A variant group (see "Recipe variants" above) hands the optimizer several versions of one dish with genuinely different nutrient vectors, which is room to manoeuvre it gets for free — the vegetarian chili closes a gap the one with mince does not. The variety constraint has to read the group, though: without it, a plan seats chili on Monday and vegetarian chili on Wednesday and counts that as two different meals, which the cook does not.

A plain greedy "cover the largest remaining deficit" pass systematically overshoots the upper bounds and cannot take anything back, and its final day is left closing whatever gap remains with whatever is available. With 7 days × n recipes the search space is small, so greedy construction plus a local swap pass (exchange a single meal whenever it lowers total cost) is cheap and produces markedly better plans.

## Handling special cases (multiple users/profiles)

* **Dietary and allergy constraints combine as a union of the prohibition lists** — an item is off-limits if it is off-limits for *any* participating profile. This single rule covers both nested diets (vegan ⊂ vegetarian falls out correctly on its own) and orthogonal constraints (diet + allergy), so no special-casing is needed.
* **Shared nutrition targets for a shared meal:** minimize the largest remaining shortfall across all participating profiles, rather than attempting to hit every profile exactly at once.

## Deliberately out of scope

* RSS feeds (Mela's differentiator, but explicitly not wanted)
* Persistent pantry/inventory management — leftover cooking runs purely on ad-hoc input, with no expiry-date tracking. Consequently, the weekly plan optimizer has no expiry data to weight against; ingredient-expiry weighting is out of scope with it.
* Camera-based automatic fridge/pantry recognition
* Factoring existing fixed eating habits (shake, cereal, kebab) into the weekly plan calculation — at least in the first version
* LoRA adapter training for personalization. Evaluated and dropped: an adapter is bound to one specific base-model version and must be retrained on every OS model update, Apple advises against it for most apps on size grounds, and it applies only to the system model — which conflicts with the swappable-backend approach. Few-shot prompting with the user's own recipes, combined with a stronger MLX model on the Mac, targets the same goal at a fraction of the cost.

## Open questions

Not fundamentally unresolved, but not yet settled in detail. Each should be decided before the phase it affects.

**Blocking phase 1:** none — the recipe data model is settled (see below).

**Recipe data model — text is the truth, structure is derived.** Ingredients and instructions are stored as written text, one entry per line, matching Mela's file format field for field. The structure needed for scaling, nutrition and shopping lists is parsed from that text on demand rather than stored in its place. The reason is that no parser understands every line: "3-4 Tomaten" scales from its lower bound, but the line itself must survive editing untouched. Storing the parse result would quietly rewrite what the user typed. Two consequences worth noting:

* Importing a Mela library becomes a direct copy rather than a conversion.
* Phase 2 cannot attach nutrition data to an ingredient by storing it on the line. It needs its own table keyed by recipe and line content, so that re-parsing does not orphan the match. Parsing is deterministic — identifiers are derived from content and position — which is what makes such a key possible.

**Amounts written into a step name an ingredient — resolved by consistency, stored only where a person overruled it.** A step reads "300 g Kartoffeln 7 Minuten köcheln lassen" while the ingredient list holds the 7,1 kg the whole dish needs. Nothing connects the two, so cook mode prints both next to each other and they contradict each other, and every further step mentioning potatoes claims the full amount over again. What a recipe never records is which ingredient a number inside a step belongs to.

* **The connection is worked out, not authored.** Which amount belongs to which ingredient is an assignment problem with hard constraints rather than a question about language, and it is solved across the whole recipe at once instead of sentence by sentence. An ingredient cannot give up more than it has, so the shares pointing at one line may not exceed its total; dimensions have to agree, so "100 g" cannot refer to a line counted in pieces; and a step's heading matches the ingredient group of the same name, which both parsers already record. Ambiguity usually dissolves under those constraints taken together: with a butter line of 200 g under "Für den Teig" and one of 100 g under "Für die Füllung", a step calling for 200 g can only mean the first, which forces a step calling for 100 g onto the second. The search space is a dozen amounts against a dozen lines — brute force with backtracking, and the same recipe therefore resolves the same way on every import, which no model can promise.
* **What stays ambiguous is mostly inconsequential.** Two lines are harmfully confusable only where their totals or groups differ; where they are identical, either choice renders the same number. Whatever is still undecided is left alone and falls back to the present behaviour — no gain there, but no regression either.
* **Only a correction is written into the text.** The resolved case changes nothing, so the stored text stays character for character what was typed — which is the rule the paragraph above sets, and which annotating on every save would quietly break. Where a person overrules the resolution, that decision is recorded in the line as a markdown link, in the scheme `RecipeLink` already uses and the editor already inserts into instruction text: `[100 g](sous://ingredient/butter?gruppe=füllung) Butter schmelzen.` When rendering, a link present wins and otherwise the resolver decides; both yield the same thing to draw.
* **The share itself is never stored.** It is arithmetic between two numbers the recipe already holds, and a stored copy would contradict them the moment the ingredient line is edited.
* **The link target is the catalog-normalized name, qualified only as far as it has to be.** Identifiers derived from line content change whenever that line is edited, which rules them out as a target; `IngredientCatalog.normalize` gives a stable key, and the catalog's aliases map "Kartoffeln" and "Kartoffel" onto the same one. A name occurring twice is qualified by its group, and one still ambiguous after that names the nth occurrence — the single form that breaks when the list is reordered, accepted because it is rare and degrades visibly.
* **Nobody types the syntax.** A correction is made where the mistake is noticed, through the suggestion bar the editor already draws by hand for ingredient lines because `TextEditor` has no inline completion: the cursor's step line offers the ingredient the resolver picked with the alternatives beside it, and taking one writes the link. Raw markdown left visible in the editor is the weak point — worth checking whether the iOS 26 `AttributedString`-backed `TextEditor` can render the link text as an accented token instead, which the editor's existing use of `TextSelection` suggests is within reach. Not assumed until tried.
* **Relative wording is resolved, never rewritten.** "Die Hälfte der Zwiebeln" is already correct at every serving count and gets a concrete amount shown beside it rather than a weight put in its place. "Restlichen" is the total minus what the other steps claim, which the same whole-recipe pass computes anyway.
* **AI is for the linguistic residue, one recipe at a time.** Wording with no lexical hook — "etwas Öl", "die Zwiebeln aus Schritt 2", "die Masse" — is reference resolution and genuinely needs language. It does not scale to a library: importing several hundred recipes from Mela is a direct copy taking seconds, and one inference run per recipe would turn it into an overnight job. The deterministic pass is therefore not the cheap substitute for the model but the precondition for bulk import working at all; the model is offered on a single recipe, on request.
* **Bare counts against a weight wait for phase 2.** "2 Kartoffeln" is a share only if the list counts potatoes as well; against 7,1 kg it needs a piece weight, which is a fact to look up in BLS rather than a number for a model to guess.
* **Consequences.** The chip under a step loses most of its purpose: once the amount is resolved into the sentence, the only ingredient worth listing separately is one a step names without any amount at all. Annotating a line changes its derived step id once, so corrections belong to editing and never to a running cook session. A reference whose ingredient has disappeared renders as its link text — degraded, not wrong. And the resolution settles a defect that exists without it: an ingredient marked as not scaling with servings holds its amount in the list while the same number written into a step scales anyway.
